# AgentFlow 系统介绍

> 面向团队讲解的完整系统说明  
> 版本：v2.7.3 | 作者：@XiaoPeng1112 | 日期：2026-06-02

---

## 一、这是什么？

AgentFlow 是一个 **AI 驱动的多 Agent 协作开发工作流引擎**，核心定位是 **Agent 编排调度中心（Orchestrator）**。

简单来说，它解决的是这样一个问题：当你使用 AI 辅助编程工具（如 Codex、Claude）时，每次只能与单个 AI 进行一次性的对话交互——你给一个任务，它返回一段代码，然后结束。这个过程中缺乏以下能力：

**流程编排**——一个完整的开发任务（从需求分析到方案设计到编码到测试到交付）由多个步骤组成，步骤之间有依赖关系和信息传递，目前只能靠人脑手动串联。

**角色分工**——不同的任务阶段适合不同"性格"的 AI（有的擅长规划拆解，有的擅长实际编码），目前无法让它们像团队一样分工协作。

**质量保障**——AI 产出的代码没有结构化的审查和合入机制，"写完就丢"，缺少类似 Code Review → Merge 的闭环。

**可观测性**——不知道 AI 在每个任务上花了多长时间、消耗了多少 Token、质量如何，无法量化也无法优化。

AgentFlow 通过 **MAF（Multi-Agent Flow）** 架构解决这些问题。它将软件开发流程拆解为 DAG（有向无环图）中的多个节点，每个节点由专门角色的 Agent 执行（Planner 负责规划、Manager 负责协调、Executor 负责编码），节点之间自动传递上下文，执行结果经人审查后合入——形成从需求到交付的完整闭环。

## 二、为什么这么做？

### 2.1 个人痛点驱动

在日常使用 AI 编程工具的过程中，积累了以下切身体会：

第一，**上下文断裂**。每次新开对话，之前的架构决策、编码风格、项目背景全部丢失，需要反复重复交代。AgentFlow 通过 Context DB（四层上下文管理）和 Context Chaining（节点间自动上下文传递）解决这个问题。

第二，**没有流程意识**。AI 工具是"点对点"的——你问一个问题，它答一个问题。但真实开发是有流程的：先分析需求，再出方案，再编码，再测试。AgentFlow 通过 DAG 工作流引擎把这个流程固化下来，让 AI 在正确的阶段做正确的事。

第三，**产出物不可控**。AI 写的代码直接 copy-paste 到项目里，没有 diff 对比、没有审批、没有版本记录。AgentFlow 通过 Git worktree 隔离 + Diff Review（类 GitHub PR）+ 三种合并策略解决这个问题。

第四，**效率黑盒**。不知道 AI 帮你省了多少时间还是浪费了时间，不知道哪个环节是瓶颈。AgentFlow 通过 Metrics 指标采集（时间、Token、质量评分）提供全链路可观测性。

### 2.2 技术趋势判断

多 Agent 协作（Multi-Agent）是 AI 应用的必然方向。单个大模型的能力虽然强大，但在复杂工程任务中，将任务分解并交给专门化的"角色"处理，整体效果远优于单一通用模型独自完成所有事情。AgentFlow 是在这个方向上的一次完整工程实践。

### 2.3 学习与探索

这个项目本身也是一次"AI + 人协作开发"的深度实验——它完全由人和 AI（CatDesk）在对话中从零搭建，是对 AI 辅助开发最佳协作模式的一次完整探索。

## 三、做了哪些？

### 3.1 核心引擎层

**DAG 工作流引擎**（三层状态机：Run → Node → Turn）是系统的心脏。支持条件分支、并行执行、Context Chaining（节点间自动上下文传递）。4 个内置工作流模板覆盖标准开发、快速迭代、Bug 修复、前后端并行四种场景。

**多角色 Agent 调度**——Planner 拆解需求、Manager 分配协调、Executor 调用 CLI 工具编写代码。Agent 通过子进程方式异步调用，WebSocket 实时推送输出流。支持 DET（确定性脚本执行）、HYB（混合模式：脚本优先，失败回退 LLM）两种额外执行模式。

**OutputContracts 合同机制**——每个节点声明"应该交付什么"，Agent 完成后系统自动校验产出物是否满足合同，确保产出质量。

### 3.2 MAF 基础设施（6 大服务）

**仓库隔离（Repo Isolation）**——每个 Run 获得独立的 Git worktree 工作空间，多个并行 Run 之间互不干扰。

**Skill 物化（Skill Materialization）**——根据白名单/黑名单策略，将 Agent 需要的技能文件物化到工作目录并注入 Prompt。

**权限隔离（Permission Isolation）**——RBAC 策略控制每个 Agent 可以访问哪些仓库和文件，deny-by-default 安全策略，全操作审计日志。

**A2A 通信协议（Agent-to-Agent）**——Agent 间的异步消息通信，支持优先级队列、ACK 确认、任务委派、广播、Channel 管理。

**合同验证引擎（Contract Validator）**——节点完成时自动比对 Agent 产出物与 OutputContract 定义，生成验证报告。

**健壮性服务（Robustness）**——指数退避重试、死信队列（失败任务不丢失）、Checkpoint 快照（任意时点恢复）、全量审计日志。

### 3.3 产出物闭环（v2.6.0）

**ArtifactMergeService**——Agent 产出代码后，系统自动在 Git worktree 环境执行 diff，将 unified diff 解析为结构化数据，前端以 GitHub PR 风格展示行级变更。支持 Squash / Merge / Rebase 三种合并策略和 Discard 丢弃操作。

这意味着 AI 写的每一行代码都要经过人的审查才能合入主分支，"AI 产出 → 人审查 → 选择策略合入" 全链路可控。

### 3.4 可观测性（v2.6.0）

**MetricsCollector**——通过订阅工作流引擎事件总线，零侵入采集全链路指标：节点耗时、Token 消耗、首次通过率、打回率、效率评分。数据持久化，跨 Session 可追溯。

前端提供四维仪表盘：Overview 概览卡片、Timeline 甘特图、Token Distribution 分布图、Efficiency 效率评分排行。帮助用户直观定位低效环节。

### 3.5 反馈闭环（v2.7.0）

**FeedbackCollector**——在三个关键触发点（审批打回、Diff 丢弃、执行失败）自动记录结构化反馈，持久化为 JSON Lines 格式。

**WeeklyDigest**——汇总 feedback + metrics 数据，输出 Markdown 周报摘要，包含执行概览、反馈统计、高频问题 Top 5、Agent 表现排行。

这是“发现问题 → 记录 → 决策改进”的最小闭环。

### 3.6 数据同步（v2.7.1 → v2.7.2）

**SyncService**——基于 GitHub Private Repo 的多设备数据同步服务。用户登录 GitHub 后，系统自动创建一个私有仓库（`agent-flow-data`）作为数据中心，通过 GitHub Contents API 实现文件级别的同步。

同步范围包括项目配置、工作流模板、Run 元数据、以及最重要的 Context DB（项目级上下文知识文件）。采用 LWW（Last Write Wins）冲突策略，系统启动时自动 pull、关键写操作后防抖 push，日常使用无感知。

**v2.7.2 多用户隔离 + 跨设备匹配**——远端仓库升级为 `users/{github_login}/` 按用户隔离结构，支持多用户共享仓库而互不干扰。核心创新是 **gitRemote 自动匹配**：添加项目时自动检测 `git remote get-url origin`，Pull 时通过 `normalizeGitRemote()`（SSH/HTTPS 标准化）自动关联不同设备上的同一项目，调用 `replaceProjectId()` 统一 ID。用户只需 clone 项目 → 添加到 AgentFlow → Pull，即完成跨设备数据对齐。

这解决了"公司电脑和家里电脑数据不互通"的痛点，确保知识资产（架构文档、决策记录、开发日志）在多设备间始终保持一致。

### 3.7 架构重构（v2.7.3）

**SQLite + WAL 持久化迁移**——将原有 JSON 文件存储替换为 SQLite + WAL 模式（better-sqlite3）。新建 `storage-sqlite.ts` 服务（~400 行），提供 ACID 事务保障和高并发读写能力。系统启动时自动检测 JSON 遗留数据并执行平滑迁移（JSON → SQLite 一次性导入），迁移完成后原 JSON 文件保留为备份。采用 `inject()` 模式解决 ESM 循环依赖问题。

**WorkflowEngine Facade 拆分**——原 1068 行的 God Object 按职责拆分为四个模块：WorkflowEngine Facade（248 行，对外统一入口）+ RunManager（564 行，Run/Node 生命周期）+ DAGScheduler（214 行，拓扑排序与就绪节点计算）+ TurnManager（271 行，Agent Turn 管理）。遵循 ADR-018 Facade 模式，外部调用者无需感知内部拆分。

**api.ts 路由拆分**——原 1575 行的单文件路由拆分为 12 个子路由文件（run、node、turn、template、project、agent 等）+ ~146 行的路由注册协调器，每个文件职责单一、可独立维护。

**新增测试**——Vitest 测试从 68 cases 增长到 122 cases，新增 dag-scheduler、turn-manager、storage-sqlite 三个测试套件，确保重构后行为不变。

### 3.8 前端可视化

- DAG 图形化视图（基于 @xyflow/react，拓扑分层自动布局，状态着色动画）
- A2A 消息面板（SVG 拓扑图 + 时间线 + 统计三视图）
- Diff Review 面板（文件树 + 行级 diff + 合并策略选择）
- Metrics 面板（4 个子 Tab：概览/甘特图/Token 分布/效率评分）
- Agent Tree 面板（树形结构展示 Agent 实例分布）
- Checkpoint 面板（Timeline 快照 + 恢复 + 健康监控）
- Context DB 编辑器（四层上下文 CRUD + 装配预览）

### 3.9 工程质量

- TypeScript 全量类型覆盖（Server + Client 零 TS 错误）
- Vitest 单元测试 122 cases 覆盖工作流引擎、DAG 调度、Turn 管理、A2A 协议、合同验证、SQLite 存储六大核心
- React.lazy 路由级代码分割，页面 chunk 独立加载
- ErrorBoundary 全局错误隔离
- 文件系统路径穿越防护 + OAuth CSRF 防护 + Agent 权限隔离

### 3.10 完整技术栈

前端：React 19 + TypeScript 6 + Vite 8 + Tailwind CSS v4 + Ant Design 6 + Zustand 5 + React Router 7

后端：Express 5 + WebSocket(ws) + Node.js 20+ + Vitest

数据持久化：SQLite + WAL 模式（better-sqlite3，高并发读写，ACID 事务保障，自动从 JSON 平滑迁移）

部署：GitHub Pages（前端静态托管） + 本地后端（需访问文件系统和 CLI 工具）

## 四、哪些不必要做？

这部分同样重要——知道什么**不做**，才能保证系统不偏离方向。

### 4.1 完整自演进系统（已明确拒绝）

在 v2.7.0 设计阶段，曾考虑实现"系统自动发现问题 → 自动决策改进方向 → 自动执行代码修改 → 自动验证效果"的完整自演进循环。最终选择不做，原因如下：

**功能冗余风险**——AgentFlow 的核心价值是"编排 Agent 完成开发任务"，不是"管理和改进自己"。如果系统花大量精力维护自身，就偏离了服务用户的根本目的。

**失控风险**——系统修改自身代码的"元循环"在数据量不足时容易产生误判，且一旦出错可能级联放大，类似于"自己给自己做手术"。

**认知噪音**——自动化建议如果精度不够，就会变成干扰而非帮助，降低系统可用性。

**最终决策（ADR-016）**：信息收集可以自动化，决策执行必须人在回路。只做 FeedbackCollector（自动采集）+ WeeklyDigest（汇总展示），改进决策由"用户读取摘要 → 与 AI 对话 → 共同决策"完成。

### 4.2 复杂数据库

没有引入 PostgreSQL / MongoDB 等外部数据库服务。v2.7.3 已将持久化从 JSON 文件迁移到 SQLite + WAL 模式（better-sqlite3），获得 ACID 事务保障和高并发读写能力，同时保持零外部服务依赖、单文件部署的轻量特性。不需要更重的关系型数据库。

### 4.3 多人实时协作

没有做 WebSocket 多客户端同步、乐观更新、CRDT 冲突解决。当前定位是本地个人工具，多人协作的复杂度远超收益。

### 4.4 CI/CD 深度集成

没有对接 GitHub Actions / Jenkins 等 CI 系统。AgentFlow 关注"从需求到代码"的创作过程，不关注"代码到部署"的运维过程。

### 4.5 约束规则（后续迭代护栏）

为了防止系统逐渐膨胀偏离方向，写入了明确的约束规则：

1. 新增功能必须复用现有 UI 容器（Tab/子视图），不新增顶级导航入口
2. 任何自动化行为默认关闭，需用户主动开启
3. 单个服务源文件不超过 300 行，超过说明职责不单一需拆分
4. 数据采集类服务只收集不决策，决策权归用户
5. 系统改进的执行方式是"用户 + AI 对话"，不是系统自动修改自身代码

## 五、能帮助到个人或团队什么？

### 5.1 对个人开发者

**让 AI 编程从"单次问答"升级为"流程化协作"**。不再是打开一个聊天框、问一个问题、得到一段代码、手动粘贴。而是定义一个工作流（需求 → 方案 → 编码 → 测试 → 交付），每一步由合适的 AI 角色自动接手，步骤之间上下文自动传递，产出物经过结构化审查后合入。

**量化 AI 辅助开发的效率**。通过 Metrics 面板精确知道：一个功能从需求到交付花了多长时间、消耗了多少 Token（成本）、哪个环节是瓶颈、哪个 Agent 效率最高。这些数据帮你优化工作流配置和 AI 使用策略。

**代码质量有保障**。Diff Review + 合同验证 + 人工审批三重门禁，确保 AI 产出的代码不会不经审查就进入主分支。

**可恢复，不怕错**。Checkpoint 快照机制让你可以在任意时点回退，Git worktree 隔离让每次实验都在安全的沙箱中进行。

### 5.2 对团队

**统一 AI 编程流程**。团队成员不再各自用各自的方式使用 AI 工具，而是遵循统一的工作流模板。需求分析怎么做、方案设计怎么审、代码编写用哪个 Agent——都有标准流程。

**知识不丢失**。Context DB 四层上下文管理 + .agent-flow/context/ 文档体系，将项目的架构决策、技术选型、开发日志全部持久化并纳入 Git 版本控制。新人 clone 仓库就能获得完整的项目认知。

**可观测性支持管理决策**。管理者可以通过 Metrics 数据了解：哪些类型的任务适合用 AI、哪些不适合；AI 辅助开发的 Token 成本是多少；团队中谁的 AI 使用效率最高——为 AI 工具投入决策提供数据支撑。

**反馈驱动持续改进**。WeeklyDigest 周报自动汇总一周内的打回、失败、高频问题，让团队能周期性地回顾和优化 AI 协作策略。

### 5.3 作为学习参考

这个项目本身也是一个优秀的工程实践案例：

- 完整的 Monorepo 全栈架构（前端 React + 后端 Express + WebSocket）
- 事件驱动的松耦合设计（Metrics/Feedback 通过事件总线零侵入采集）
- 三层状态机 + DAG 编排引擎的实现方式
- TypeScript 全量类型安全 + Vitest 单元测试最佳实践
- 产品从 0 到 1 的完整设计思考和技术决策记录（18 个 ADR）

## 六、未来的预期和发展

### 6.1 短期（当前可用）

当前 v2.7.3 已经是一个功能完整的闭环系统：

```
需求输入 → DAG 编排 → Agent 执行 → 人工审查 → Diff Review → 合并/丢弃
     ↑                                                            ↓
     ← ← ← ← ← Feedback 反馈 ← ← ← ← ← ← ← ← ← ← ← ← ← ←
```

v2.7.2 新增的多用户隔离 + gitRemote 跨设备自动匹配能力，让用户可以在多台设备间无缝切换工作，数据自动互通。v2.7.3 完成了 SQLite 持久化迁移和 WorkflowEngine 架构拆分，系统稳定性和可维护性大幅提升。

可以直接在个人开发中使用，验证“AI 多角色协作开发”这套流程是否真的能提升效率。

### 6.2 中期演进方向

**数据积累驱动优化**——随着使用时间增长，feedback + metrics 数据积累后，可以针对性地优化工作流模板（比如发现 review 节点打回率过高 → 在 implement 节点增加自检步骤）。

**模板生态丰富**——基于实际使用经验沉淀更多工作流模板：重构流程、性能优化流程、文档撰写流程、测试补全流程等。

**数据持久化升级**——✅ 已在 v2.7.3 完成 SQLite 迁移，启动时自动从 JSON 平滑迁移。

### 6.3 长期愿景

**成为团队标准工具**——从个人使用推广到团队层面，提供多人协作能力（WebSocket 同步 + 冲突解决），让团队共享工作流模板和最佳实践。

**插件化扩展**——支持自定义 Agent 类型（对接更多 AI Provider）、自定义节点类型（对接外部系统如 Jira / GitLab），通过插件机制而非源码修改实现扩展。

**行业方案沉淀**——针对不同场景（前端开发、后端开发、移动端开发、数据工程）沉淀专业化的工作流模板和 Agent 配置。

### 6.4 关于"自动化"的克制

系统未来的演进始终遵循 ADR-016 的核心原则：**信息收集可以自动化，决策执行必须人在回路**。系统会越来越擅长"收集和呈现信息"（更好的数据可视化、更精准的问题识别、更有价值的周报摘要），但"改什么、怎么改"的决策权永远属于使用者。

这不是技术能力不足的妥协，而是设计哲学的选择——AI 是工具不是替代品，流程的改进需要人的判断力和业务理解。

## 八、总结

AgentFlow 的本质是把"人使用 AI 工具"这件事从**随机的、碎片化的、不可追溯的**状态，升级为**流程化的、结构化的、可量化的**状态。

它不试图取代人的判断力，而是让 AI 在正确的框架内发挥最大效能——通过 DAG 编排给 AI 明确的任务边界，通过 OutputContracts 给 AI 明确的交付标准，通过 Diff Review 给人明确的审查入口，通过 Metrics 给团队明确的效率数据。

如果用一句话概括：**AgentFlow 是让 AI 编程从"聊天"升级为"协作"的引擎**。
